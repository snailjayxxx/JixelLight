# F5 M77 — verified move import and reviewed recovery

Move import is a separate bilingual Import action for new local photos outside the current saved project. It shares the existing filename/date preview,1–1000-file planning, cancellation, verified byte copy and no-overwrite destination rules. Copy/Add behavior is preserved. Move explicitly explains that original files enter system trash only after verified copies and content identities have been saved in the project. It never permanently unlinks an original. Unavailable trash retains copies and remaining originals.

## Two-phase handoff

A bounded background worker first copies and SHA-verifies. Each completed publication is recorded atomically in a process-owned `.jixellight-move-*/move.json` directory at the destination. A failed journal write stops further publication; completed copies and all unretired originals remain. A canceled/failed first pass can import completed copies, but cannot authorize retirement in that pass.

The GUI owner imports completed destinations, records their full SHA-256/size identities and flushes the project. A separate worker rereads the saved catalog and verifies the entire destination/source set before the first retirement. Each file is rechecked immediately before its trash operation, with an on-disk intent followed by its outcome. Originals already referenced by the active catalog are refused; existing source families use the independent relink workflow. Symlink sources, duplicate/overlapping plans, changed/unreadable files and unknown saved identities cannot authorize retirement.

A canonical journal lock serializes retirement. The parser validates the bounded record before any sibling lock is created, then rereads under the lock. The raw journal digest must still match its accepted snapshot. Successful retirement uses [Qt's system trash API](https://doc.qt.io/qt-6.8/qfile.html#moveToTrash), with no permanent-delete fallback. Where the platform reports a trash location, its bytes are checked; a raced replacement is restored only to an unoccupied original path or marked for manual review. Platforms may report no trash path. Completed journal entries never authorize acting on a new file subsequently created at the old source path.

## Recovery and ownership

The recovery dialog asynchronously loads a bounded2MiB record and shows the concrete source/destination rows and localized state. Reading never moves files. Resume requires a valid review in the record's current project and its unchanged digest; the worker rechecks both record and saved byte identities. Project switches invalidate the review. Copy/import and retirement share busy/cancel/close ownership, and project changes cannot interrupt an active transfer. Closing collects completed copies and preserves unprocessed originals.

Recovery is explicit, never automatic at startup. The latest record path is a device preference. Source locations, hashes, counts, backend and phase are retained in actions/diagnostics. Original Develop/history/curation, working images, scopes and export remain separate from transfer state. Failed/canceled copies or a crash between an OS trash action and its outcome record retain the destination and recoverable trash; ambiguous missing sources require manual review. Forced-process-kill/power-loss recovery is not claimed validated by the native fixture.
