# F4 M11 — Point Color CPU reference and working-color picker

This stage adds one optional Point Color selection to the existing photo editor. It is a CPU implementation. Metal/Direct3D/OpenGL can present a complete CPU reference upload; they do not compute Point Color in this stage. Existing originals, RAW decoding, Sony profiles, operation deadlines, parity limits and brush budgets are unchanged. Whole-product development is incomplete.

## Behavior

The independent controls enable/disable a selection, choose an sRGB color through the dialog, pick a color on the actual photo canvas, adjust hue ±180°, saturation ±100 and lightness ±100, adjust hue/chroma/lightness ranges, and reset this section. Disabled custom controls/selection remain stored for re-enabling. Reset restores factory values and preserves all unrelated edits. The bilingual panel marks CPU processing and its fold state persists. Range labels have sufficient width in the 300/320/350 px panel checks.

A selection is stored as working Oklab, before output gamut, transfer, LUT, grain, detail and monitor ICC. `pointColor` is optional strict schema 1 with exactly `schema,space,enabled,center,hue,saturation,luminance,hueRange,chromaRange,lightnessRange`; `space` must be `oklab`, and finite center coordinates lie within ±4. Other ranges retain their explicit finite bounds. Factory disabled state is omitted. Old snapshots without the section preserve their existing pixels and settings. No prior stage is reordered; this new conditional operation is appended inside the existing PerceptualLook boundary. Full state/packed-plan cache keys distinguish it, while upstream denoise/dehaze/texture/clarity keys exclude downstream Point Color edits. The Sony engine/profile compatibility string remains unchanged.

Three soft range weights multiply. Each weight is 1 inside half its radius, 0 at/outside the radius, and has a smoothstep shoulder between. Hue distance is circular; hue confidence tapers through very low chroma, and a 180° hue radius includes the full circle. The weighted adjustment rotates Oklab a/b by the selected hue shift, scales chroma by `1+saturation*.01*weight`, and adds `lightness*.003*weight` to L. Values remain unclipped until the existing output boundary. Zero/disabled/unselected pixels bypass the Lab round trip exactly. Alpha is unchanged. This is an independent implementation; no equivalence to another editor or broad photographic quality acceptance is asserted.

## Integration and sampling

The picker renders only the summed spatial neighborhood for one preview pixel, with the existing input interpretation and frozen whole-frame dehaze airlight. It includes denoise, dehaze, texture, clarity, WB/exposure, local linear/radial/brush exposure, vignette, highlight recovery, tone, HSL, Sony styling, B&W and grading. It excludes Point Color itself and all subsequent output/display operations. Transparent locations, invalid FP32 input/settings, cancellation and invalid coordinates refuse sampling. Brush sampling retains the existing document/frame/work admission bounds; its small neighborhood introduces no whole-frame intermediate.

`LatestJob` holds immutable source/plan/point/photo/generation/revision snapshots. Sampling runs off the GUI thread; changed photo, preparation generation or render revision prevents a stale result from committing. Brush drawing/recovery, crop editing and incomplete rendering block the picker. A successful sample records one selection command/history action, then preserves existing amount/range controls. The canvas tool can be cancelled with Escape.

All six controls join the shared 30-parameter registry. Strict commands are `point.color.enable`, `point.color.select` (encoded sRGB), `point.color.select.lab` (working coordinates), and `point.color.reset`. The existing color transfer group includes the selection and controls. Projects, virtual copies, history, presets, XMP, diagnostic snapshots, CLI and export use the same state. Invalid writes/history/copies refuse atomically; invalid project opening preserves the current catalog and source database bytes.

The packed plan appends three slots after the existing 58-slot prefix: adjustment 58, center 59, range 60; total 61 vec4/976 bytes. Every shader declaration matches that size. Inactive slots must be zero. Active packed ranges/finite values/reserved components are validated. Ordinary GPU previews select `point-color-cpu-stage`; diagnostics say `cpu-reference-upload` and `point_color:cpu-reference`. Native brush admission selects the existing CPU policy. No extra Point Color image plane, spatial halo or per-pixel allocation is introduced.
