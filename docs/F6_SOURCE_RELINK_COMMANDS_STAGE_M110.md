# M110: Shared desktop source-relink commands

Strict `photo.relink.request`, `photo.relink.confirm` and `photo.relink.cancel` share the existing desktop begin/confirm/cancel APIs and native dialog. Request binds the exact saved version, native candidate path and current decimal catalog token. Confirmation binds the exact request ID, catalog token and explicit boolean unknown-identity acknowledgement. Cancellation binds the matching request or retained preview; an empty ID is valid only when neither exists. Malformed, extra, NUL, oversized or noncanonical identifiers refuse before file access or caller-output changes. Relative paths are frozen as absolute paths before callbacks. Public adapters reject foreign threads and closing owners before reading controller state.

The original two full-file SHA-256/fresh-decode validation passes, size limit, known-identity matching, unknown-identity acknowledgement, captured version family, SQLite transaction, cache invalidation and original read-only behavior remain. Request success means queued for validation; confirmation success means queued for revalidation, never a claim that a transaction has already committed. Canonical accepted-command traces freeze project and command facts before callbacks and do not read a destroyed owner afterwards. Internal catalog cleanup retains its private cancellation path.

Starting a request no longer retains a photo iterator across the cancellation signal. Target, identity and family are staged before callbacks; owner, catalog epoch, request generation, active operations and family are rechecked before queueing. A callback that changes the catalog, starts a newer request or destroys the owner prevents the older request from publishing. Confirmation also rechecks owner/request/epoch/family after the durable-save barrier. Cancellation of a stale catalog or request cannot clear the current review.

Core covers strict field/identifier/path decoding and untouched output. Three new missing-source cases exercise real foreign-thread refusals without cancelling a ready review, stale catalog/request commands, reentrant catalog changes/owner destruction, and replacement-request precedence with original/candidate bytes unchanged. Existing known-family recovery now uses actual request/confirm commands while retaining exact exported pixels, version histories, metadata and reopen checks. The normal native Relink flow requires exact request/cancel/request/acknowledged-confirm traces through the existing pointer-driven dialog; all previous conditions, screenshots and 20s/30s deadlines remain. CLI/session checks reject late desktop relink commands before earlier outputs; the original82 CLI categories remain, with two appended categories.
