## CLI examples

```sh
JixelLightCli --schema
JixelLightCli --commands adjustments.json --space display-p3 input.ARW new-output.png
JixelLightCli input.jpg new-output.jpg
JixelLightCli --batch exports.json
JixelLightCli --catalog Project.jlp --output-dir existing-folder --format png
JixelLightCli --catalog Project.jlp --output-dir existing-folder --commands adjustments.json --format jpeg
```

`adjustments.json`:

```json
[{"command":"develop.set","parameter":"exposure","value":0.5}]
```

Example `exports.json` (use the engine reported by `--schema`):

```json
{"schema":1,"engine":"jixellight-linear-v5-base2-look4","jobs":[
  {"source":"input.ARW","destination":"variant.png","space":"display-p3",
   "commands":[{"command":"develop.set","parameter":"exposure","value":0.5}]}
]}
```

CLI shares the existing scalar/HSL/curve ranges and clamps finite numeric values. It also supports normalized `geometry.crop`, absolute `geometry.straighten` (−45° to +45°, outside this range is rejected), relative integer `geometry.rotate`, flip toggles, geometry reset, curve reset and Develop reset. Unknown fields, invalid indices and invalid geometry are rejected without partial state changes. It uses CPU reference processing, As Shot look resolution and camera baseline metadata; it never downloads models or opens a remote service. GUI Undo/Redo snapshots and the cursor are persisted atomically with current adjustments in the catalog adjustment JSON (`_history`, schema 1). Legacy projects without history initialize from their current state. Unknown or corrupt histories reject project opening before replacing the active writer. Shared Sony LUTs are serialized once per photo history and validated on restore, including the same fitted-engine compatibility rule as Look profile imports. Persisted/copied/synced/preset As Shot state preserves the symbolic user request; camera-derived code/parameters are resolved only for rendering. Earlier draft histories with only stale resolved As Shot metadata differences are restored to the exact user snapshot, while differing scalars/strength are rejected. Failed writes remain sticky per category/photo until the same data is successfully retried; GUI recovery retains history and catalog annotations too.

User-local named presets live in the application data directory and use atomic writes. Save/import refuse duplicate names; Rename refuses collisions; Update is a separate operation with GUI confirmation. Unreadable/unknown-version files remain protected. Portable `.jixelpreset.json` files validate the current rendering engine and full Sony state, exclude geometry/curation and use a same-folder temporary file with a non-overwriting final rename; importing requires an unused name and never applies the preset to the active photo automatically.

Diagnostic ZIPs include `stage_outputs.json` and the same structured data in their manifest. SHA-256 hashes stream visible native QImage rows without copying full frames or hashing row padding; format/dimensions/engine are included and ICC bytes are hashed separately. These are the actual RGBA64/proxy and CPU output boundaries, before monitor presentation, not float RAW, GPU readback or individual color-kernel hashes. Hashing runs only on the explicit diagnostic action and records its elapsed time. Capture renders the current parameters/geometry even before asynchronous preview refinement. Each ZIP has a unique filename and refuses existing destinations. Reused CMake builds track Git HEAD/ref changes so commit metadata does not stay at the initial configuration.

`--batch` accepts a schema-1 JSON object with the exact current engine and 1–1000 jobs (4 MiB limit); each job requires `source`, `destination` and a shared-command array, with optional `space`. Relative paths use the manifest directory; `--space` is the per-job default. All commands, readable source paths, existing parent directories and distinct new destinations are validated before rendering. Destination aliases/case-only duplicates are rejected. Both single and batch CLI exports render inside a unique temporary directory on the destination filesystem and publish with a non-overwriting rename, including protection against destinations appearing after preflight.

`--catalog` reads all saved original/virtual versions through the same catalog/history/Sony validator in one read-only SQLite transaction. It never adopts a writer, changes journal mode, upgrades tables or changes saved edits. Relative source paths use the `.jlp` directory; output names have a deterministic version index. It exports the saved history cursor and Sony/geometry snapshot, rather than reusing defaults from a different version. Optional `--commands` modify each export snapshot without persisting changes. Both multi-job modes stop on a runtime decode/render/publication failure, retain completed output files, exit 2 and emit JSON with completed/failed/not-attempted counts; success exits 0. This is sequential offline CPU processing; JPEG quality is 92 and output folders must already exist.

## XMP, interactive crop and additional output formats

- XMP is an explicit current-version operation from Project / Export menus. Standard namespace URIs identify rating, color label and Dublin Core keyword Bag; arbitrary prefixes and attribute/element forms of simple properties work. JixelLight state is a versioned JSON snapshot in its own namespace. Adobe Camera Raw properties are not translated. Missing public properties preserve current values; imported public values override the private snapshot when an external editor changes them. An unsupported custom label is reported and leaves the current color alone. Reject uses public rating -1 while the private snapshot preserves the independent star rating.
- Full parsing and engine/Sony/geometry/catalog validation precedes mutation; duplicate/structured unsupported known properties, malformed XML, DTD/entities, oversized/deep documents and future snapshots are rejected. Import applies to the current original/virtual version only; Develop is one undoable step, while annotations follow existing non-undoable catalog semantics stated in the confirmation. Writes require a new .xmp destination, stage in a same-directory temporary directory and publish without replacing existing files. Other software's XMP and source photo bytes remain untouched; this is not an in-place merge or automatic discovery feature.
- Crop edits temporarily show the full oriented photograph, without changing saved/exported state. Eight handles, moving, free/fixed ratios, Full, Apply and Cancel operate on a draft. Applying inversely maps visual coordinates to the normalized source grid (after optional straighten, before orientation) and creates one history step. Cancel, another Develop action and photo changes discard the draft. Exact and preview Scopes describe the visible full photo during editing, explicitly labeled, and return to the committed crop after Apply/Cancel. Geometry remains CPU preparation before the color engine.
- TIFF/WebP use the Qt 6.8.3 Image Formats codecs, with plugin installation in build and release workflows. TIFF retains RGBA64 and lossless LZW; WebP receives target-ICC-converted RGBA8888 and uses 1–100 quality (100 selects lossless). GUI current/batch and offline single/batch/catalog paths support both. CLI preflight verifies codec availability before processing any job. TIFF/PNG/WebP encode the full rendered frame in memory; cancellation is checked before publication, but the codec itself is not interruptible.
- Tests verify all 16 orientation/flip crop mappings against actual pixel regions, draft/commit/cancel/Undo/photo switching, XMP namespace/escaping/duplicate/entity/future-engine behavior and per-version durable import, and TIFF/WebP exact round trips across all four ICC spaces with explicit RAW/non-RAW semantics. The independent packaged CLI validator inspects TIFF bit depth/LZW/ICC and WebP RIFF/ICC and reimports both through the deployed readers, with existing-output refusal, catalog state and original/database-byte preservation.

Reference definitions: [Adobe XMP Basic](https://developer.adobe.com/xmp/docs/xmp-namespaces/xmp/), [Dublin Core XMP](https://developer.adobe.com/xmp/docs/xmp-namespaces/dc/), [Qt Image Formats](https://doc.qt.io/qt-6.8/qtimageformats-index.html). No external source code or image assets are copied.

## Optional waveform, RGB Parade and vectorscope

- The pinned panel can switch from the existing default GPU histogram to CPU reference plots. Waveform and Parade aggregate 256 horizontal positions and 1024 vertical levels; Parade retains independent RGB counts. Vectorscope uses a 512 × 512 grid of encoded sRGB Cb/Cr, with matching 100% RGB/CMY targets. These are encoded photo-output values, not video IRE, nits, a RAW sensor scope or a new GPU scope kernel.
- Immutable requests use the same processing plan, geometry and 128-row region path with Sony detail halos as exact histogram/JPEG. Full-resolution plots count every output pixel; preview plots describe the currently prepared viewport. Monitor ICC never changes counts or the UI plot ink. Density uses logarithmic display intensity and a three-pixel trace; neither changes the underlying counts. The image provider scales plot axes independently so a tall 1024-level waveform does not lose horizontal resolution to aspect-fit downsampling.
- Work is optional, debounced and cancellable with one running/one replaceable pending request. Revision/mode/resolution guards discard stale results; previous visible results dim while updating. Photo changes, empty projects and histogram mode clear the image. Crop editing uses the explicitly labeled full oriented draft preview. Allocation/render errors have visible status; explicit diagnostic bundles record plot mode, revision, pixel count, resolution and current/error state.
- Core coverage checks endpoints and independent channel totals, neutral and red chroma, full-frame versus tiled rendering across Sony-detail boundaries and RAW/non-RAW semantics, crop pixel counts, rapid parameter/mode/photo changes, empty-project clearing, provider sizing and monitor separation. RAW GUI smoke visits all three plots at full resolution and verifies current images and exact pixel counts, then restores histogram mode.

The new plots currently run on the CPU and do not replace or weaken mandatory GPU histogram/color parity checks. Counting is bounded by the small fixed grids plus rendered rows, while source geometry can still allocate a full image as before.


## Non-destructive straighten

- Absolute clockwise angles from −45° to +45° apply before 90° orientation and flips. A centered rectangle is inscribed in the rotated source, preserving the sample-grid aspect and never upscaling. Dimensions shrink to keep every inverse-mapped pixel center within the source; one-pixel-wide sources reduce to their center sample. Manual crop follows this correction, so the full-image crop overlay matches the visible corrected image. Changing the angle retains normalized crop fractions on the corrected grid.
- A cancellable CPU pass bilinearly samples linear RGBA64, interpolating premultiplied values to avoid transparent-color bleed and returning unassociated RGBA64. ICC, source text and density/DPR metadata survive. Zero degrees retains the prior no-resampling path exactly. Geometric preparation still precedes GPU color processing; this is not a float RAW upgrade, perspective correction or automatic horizon detection.
- Nonzero angles use geometry schema 2 with an explicit `straighten` field. Zero angle serializes exactly as legacy schema 1, so old histories and presets remain canonical. New readers reject unknown/invalid geometry before changing a project writer, including records without history. Histories, virtual copies, XMP and CLI snapshots preserve the angle; named Develop presets continue excluding all geometry. Angle controls coalesce one drag into one undo step, while the 0° control ends the preceding gesture.
- GUI previews, exact histogram, optional plots, JPEG and raster exporters share the implementation and cancellation token. Geometry JSON participates in preview cache keys and diagnostic dependencies; `geometry_straighten` records CPU timing. Existing Sony engine identifiers, RAW defaults and GPU tolerance remain unchanged.
- Tests compare every sample of affine 16-bit ramps against independently calculated coordinates at positive/negative and boundary angles, check opaque corners, alpha behavior and tiny sources, and verify crop/orientation order, cancellation, prepared-preview/export/scope agreement, cache invalidation, coalesced Undo/Redo, reopen at an undone cursor, XMP and ICC round trips. Deployed CLI tests exercise angle parsing, dimensions, catalog overrides and future-geometry refusal without mutating source/catalog bytes.
