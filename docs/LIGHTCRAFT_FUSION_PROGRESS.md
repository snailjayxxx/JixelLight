## GPU diagnostic capture (acceptance pending)

The interactive Report action requests one asynchronous RGBA32F working-output readback before monitor ICC. Canonical little-endian IEEE-754 RGBA hashes preserve signed zero/NaN payloads, ignore row padding, and record finite per-channel ranges and nonfinite counts. Metadata identifies the rendered revision, source cache key, output space/backend and actual producer (`gpu-compute` or `cpu-reference-upload`). The CPU preview in the ZIP remains a frozen CPU reference, with a separate CPU oracle for the same frozen GPU input/plan; hashes do not assert numerical parity between native compute and the quantized CPU oracle.

Normal editing still reads back only 16,400 histogram bytes; the explicit frame readback is capped at 64 MiB, accounted separately, drained safely at engine teardown/resize, and releases pixel bytes after hashing. A pending report has a 3 s response deadline; unavailable/oversize/changed/failed/timed-out GPU capture still produces a useful frozen CPU report. Old request IDs and mismatched revision/source responses cannot attach a previous frame. Synchronous `reportBug()` remains CPU-only. The UI prevents overlapping reports; headless `requestBugReport()` emits `diagnosticFinished` without a dialog.

`--diagnostic-smoke-report` uses an owned 64×48 PNG in a separate 15 s GUI check, leaving the main RAW smoke deadline untouched. `tools/ValidateDiagnostic.py` verifies the actual diagnostic ZIP/manifest/CPU fallback and GPU snapshot; mandatory desktop/Linux GUI and deployed GPU/CPU packages run it. Core tests cover bit identity/ranges/budgets and frozen/stale/mismatched/timed-out delivery; mandatory QRhi tests compare a separate texture readback, CPU producer labels, refusal/source-upload invariance and pre-monitor output across actual display drawing/teardown. Internal GPU boundaries, individual kernel timings and true float RAW remain unfinished.

## CLI examples

```sh
JixelLightCli --schema
JixelLightCli --commands adjustments.json --space display-p3 input.ARW new-output.png
JixelLightCli input.jpg new-output.jpg
JixelLightCli --batch exports.json
JixelLightCli --catalog Project.jlp --list-catalog
JixelLightCli --catalog Project.jlp --catalog-key "key-from-list" --output-dir existing-folder --format png
JixelLightCli --catalog Project.jlp --output-dir existing-folder --format png
JixelLightCli --catalog Project.jlp --output-dir existing-folder --commands adjustments.json --format jpeg
JixelLightCli --catalog Project.jlp --output-dir existing-folder --format png --name-template '{capture_date}_{name}_{version}_{seq:4}' --sequence-start 7
```

`adjustments.json`:

```json
[{"command":"develop.set","parameter":"exposure","value":0.5}]
```

Example `exports.json` (use the engine reported by `--schema`):

```json
{"schema":1,"engine":"jixellight-linear-v5-base2-look4","jobs":[
  {"source":"input.ARW","destination":"variant.png","space":"display-p3",
   "commands":[{"command":"develop.set","parameter":"exposure","value":0.5}]}
]}
```

CLI shares the existing scalar/HSL/curve ranges and clamps finite numeric values. It also supports normalized `geometry.crop`, absolute `geometry.straighten` (−45° to +45°, outside this range is rejected), relative integer `geometry.rotate`, flip toggles, geometry reset, curve reset and Develop reset. Unknown fields, invalid indices and invalid geometry are rejected without partial state changes. It uses CPU reference processing, As Shot look resolution and camera baseline metadata; it never downloads models or opens a remote service. GUI Undo/Redo snapshots and the cursor are persisted atomically with current adjustments in the catalog adjustment JSON (`_history`, schema 1). Legacy projects without history initialize from their current state. Unknown or corrupt histories reject project opening before replacing the active writer. Shared Sony LUTs are serialized once per photo history and validated on restore, including the same fitted-engine compatibility rule as Look profile imports. Persisted/copied/synced/preset As Shot state preserves the symbolic user request; camera-derived code/parameters are resolved only for rendering. Earlier draft histories with only stale resolved As Shot metadata differences are restored to the exact user snapshot, while differing scalars/strength are rejected. Failed writes remain sticky per category/photo until the same data is successfully retried; GUI recovery retains history and catalog annotations too.

User-local named presets live in the application data directory and use atomic writes. Save/import refuse duplicate names; Rename refuses collisions; Update is a separate operation with GUI confirmation. Unreadable/unknown-version files remain protected. - Forward operation order is lens/CA -> perspective -> clockwise straighten -> normalized crop -> quarter-turns/flips -> color. All active corrections and straighten use one backward RGBA64 bilinear resample. It covers every sample, including curved edges, avoids stretched invalid borders and never enlarges output dimensions.
