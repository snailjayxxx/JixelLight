# F5 M76 — bounded, presentation-only soft proof

Soft proof is an optional folded bilingual Develop panel. It defaults off on each launch. The selected built-in sRGB/P3/Adobe/ProPhoto or local RGB/CMYK display/output ICC, rendering intent, paper-white simulation, black-point compensation and magenta gamut warning are device preferences. They never become Develop/history/project/preset/XMP/command fields. Custom ICC files are bounded to4MiB and frozen by content; a remembered path must still match the saved hash on the next launch. Invalid choices leave the existing profile unchanged.

The independent CPU worker renders the current immutable prepared source directly to encoded gamma1.8 ProPhoto, then LittleCMS proofs this wide-gamut image through the chosen output profile to encoded sRGB. The established monitor provider applies its existing display transform once. This avoids losing out-of-gamut information through an early clipped sRGB frame. The ProPhoto profile correction in M75 is a separate parent commit; output pixel algorithms and engine compatibility remain unchanged here.

Proofing uses a per-job LittleCMS context, error handler and alarm codes. User rendering intent describes the target-device conversion; the proofing intent is relative colorimetric or absolute colorimetric for paper simulation. SOFTPROOFING/GAMUTCHECK and black-point flags follow the selected controls. Alpha is copied exactly, transformations check cancellation by row, and profiles/transforms/context are job-owned. The implementation follows the official [LittleCMS tutorial](https://www.littlecms.com/LittleCMS2.18%20tutorial.pdf) and [pipeline API](https://www.littlecms.com/LittleCMS2.18%20API.pdf), with a separate synthetic CMYK device model for tests; no vendor printer profile or measured print result is claimed.

## Admission and asynchronous ownership

Proof source pixels are capped at8Mi. One immutable resized-source slot is reused, with its own shared budget lease. Four RGBA16 presentation planes are reserved (32 bytes per proof pixel). The CPU operation separately reserves the existing conservative whole-frame estimate, including spatial/detail/mask work, against the unchanged shared3GiB budget. The worker reuses the bounded CPU spatial caches. The original32Mi brush source limit and strict brush public admission are retained.

A private prepared-image reservation validates retained original intent and every packed parameter for ordinary photos. Brush-bearing proof plans continue through the original strict BrushRenderRequest path. No artificial brush is created and no unused source is deep-copied. A regression explicitly rejects mutated packed plans and brushless requests through the old brush-only API; another validates committed Paint/Erase proof and complete lease release.

LatestJob has one running and one replaceable pending job. A150ms debounce,60s deadline and budget retry handle interaction without publishing old work. Photo epoch, preparation, render revision, generation, immutable CPU preview source and separate GPU staging source all guard publication. Source/edit/viewport changes immediately retire the old provider URL. Active brush gestures pause proof and resume afterwards. Monitor changes regenerate/rename only the existing display copy. Read-only image aliases retain the admission lease even after the provider replaces its slot. The proof provider returns its bounded native image rather than allocating an arbitrary requested size.

## Canvas, diagnostics and original-image invariants

The proof image has a separate versioned provider slot. The ordinary GPU renderer continues computing working pixels and scopes while its presentation is transparently covered, so half-alpha proof pixels are composed once. Existing committed/reference/brush/scopes slots remain independent. Disabling proof restores the original preview and invalidates the old proof URL.

Frozen bug ZIP performance values record proof target/hash, source/revision/generation, intent, flags, size, memory charges and state. The ZIP's original working stages, original CPU image and actual GPU working output remain the edit result. No new per-pixel GPU tolerance claim is substituted for the existing GPU suite.
