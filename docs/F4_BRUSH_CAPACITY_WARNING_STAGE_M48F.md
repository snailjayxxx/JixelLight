# F4: capacity warning for long brush gestures

A long brush or eraser gesture can reach the existing per-stroke or document dab limit. Previously the application could cancel the gesture at the limit with no advance warning. A visible bilingual warning now appears once a positive-pressure gesture has accumulated approximately three quarters of the smaller available limit. It clears when the gesture ends or is cancelled; zero-pressure-only input does not display it. The existing 4,096-dab per-stroke and 16,384-dab document limits, work budgets and color pipeline are unchanged.

This warning gives an opportunity to release a stroke; it does not guarantee that the stroke can be committed. A single large input event can cross the limit between updates. With only one document dab remaining, a zero-pressure start followed by positive pressure at a different position can still be refused without changing image or history. Continuously varying subpixel-pressure jitter remains unresolved; the warning is a mitigation, not a repair of that regression.

For one narrow case that previously refused a stroke, if exactly one document dab remains and the finished stroke contains only two dabs at the identical coordinates with exactly one at zero pressure, the zero-pressure endpoint is omitted for both live preview and commit. The positive dab and geometric selection point remain. Strokes that already fit, distinct positions and all other input retain the existing behavior. A finite CPU comparison across 288 paint/erase, pressure, hardness, opacity and viewport cases found bitwise-identical exposure and RGBA output before and after this same-center omission, including exact alpha. This is a finite model, not a proof for physical hardware.

## Formal Root validation

The app, gesture tests, Core tests and export verifier built serially. The registered 69-test plan kept the existing 120-second gesture shard; an isolated CTest driver ran the same nine registered gesture methods with only its working directory and output path isolated, with 11 Qt pass records including setup/cleanup and no failures or skips. Existing capture-queue and low-pressure Core checks and eight screenshot-failure tests passed.

Four controlled UI runs used the formal Root product controller and QML objects with a test-only smoke entry. CPU/Metal, 1×/2×, opaque/transparent, paint/erase and English/Chinese scenarios exercised the warning, real-time preview, one-dab commit and Undo/Redo in 1,657/2,070/2,041/2,298 ms. Five screenshots per run were checked by CRC and SHA; independent ImageIO decoding confirmed matching canvas pixels for preview/commit/redo and baseline/undo. The first native UI process exited 0, but its original validation guard exited 1 because a sealed decoder copy lacked executable permission. The original failure and images were retained; a same-hash executable copy independently rechecked the original screenshots without rerunning that native UI. The other three UI runs and the follow-up guard exited 0. Controlled QPA stylus events do not verify a physical tablet.

The original CPU/Metal pressure workflow passed eight 1×/2× opaque/transparent runs under the existing 45,000 ms limit, retaining 22 PNG85 images per run and the original pressure, scope, plan and exact-export checks. A deliberately blocked PNG write produced the expected native exit 1 and retained a verified failure image. The independent local audit checked 219 images in total.

Public real Sony ARW CPU/Metal pressure regressions completed their GUI in 10,425/10,277 ms and export plus independent reference in 35,628.3/34,458.362 ms. Each retained 32,947,264 source, histogram and waveform pixels, the shared 3 GiB reservation and exact PNG16/ICC under the original 60,000/120,000 ms limits. Peak reservations were 1,716,323,360/1,720,467,584 bytes. The original Sony native reports retain their external-verification-pending state; the independent verifiers and complete drivers exited 0. These are existing pressure regressions, not physical tablet or new jitter-specific Sony tests.
